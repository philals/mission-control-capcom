# Address a pull request

Argument: `<PR-URL>` (for example `https://github.com/acme/api/pull/12`). It may be followed by a note such as "automatic round 2 of 5". When a round is automatic nobody is watching, so never stop to ask a question: do what is clearly right, leave anything doubtful alone and say so in the summary.

## Rules

- Work only on the PR's own branch. Never push to the default branch, never force-push, never rewrite history, never merge the PR, never mark it ready or draft, never close it.
- Bring the branch up to date by **merging** the default branch in (not rebasing: the repo's history and its merge bot use merge commits).
- Make every change of a round in as few commits as you can and push **once** at the end. Each push starts a new CI run that cancels the one before, so many small pushes waste CI.
- Never run a full local test suite (it blocks the machine). Run lint, typecheck, build or the specific tests that cover what you changed. Let CI run the rest.
- Do not invent fixes for failures that are not about the code (an outage, a missing secret, a flaky test that passes on rerun). Say so and stop.
- Only touch conversations on this PR.

## Steps

1. **Find the PR and the checkout.** `gh pr view <PR-URL> --json number,headRefName,baseRefName,state,isDraft,headRefOid,headRepository`. Stop if it is not open. Find a local checkout of the PR's repository that has the head branch checked out (`git worktree list` in the repository; a worktree whose branch is `headRefName` is the one to use). If the branch is not checked out anywhere, make a worktree for it with `gh pr checkout` semantics (`git fetch origin <branch>` then `git worktree add`), and do all the work there. If you cannot find the repository on disk, stop and say where you looked.
2. **Bring in the default branch.** `git fetch origin`, then `git merge origin/<baseRefName>` into the PR branch (do not push yet). If it conflicts, resolve conflicts that are plainly mechanical (neighbouring edits, import order, lockfiles regenerated by the package manager). If a conflict is a real disagreement about behaviour, `git merge --abort`, skip the merge for this round, and say so.
3. **Collect what needs doing.**
   - **Comments:** the unresolved review threads, with their ids:
     `gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){reviewThreads(first:100){nodes{id isResolved isOutdated path line comments(first:20){nodes{author{login} body}}}}}}}' -f o=<owner> -f r=<repo> -F n=<number>`. Keep the threads where `isResolved` is false.
   - **CI:** `gh pr checks <PR-URL>`. For each failing check (ignore ones that are only `cancelled`: a newer run replaced them), find its run and read the failing part: `gh run view <run-id> --log-failed`.
4. **Decide, one by one.** For each unresolved thread choose:
   - **Fix** it, when the comment is right or reasonable.
   - **Decline** it, when it is wrong, already handled, or contradicts how this code base does things. Be able to say why in one sentence.
   - **Leave** it, when it needs a human decision (a product or design choice, or you are unsure). Do not resolve these.
   Copilot's comments are often fine and sometimes wrong. Read the code before deciding; do not apply a suggestion just because it was made.
5. **Make the changes.** Apply the fixes, and the fix for each real CI failure, in the working tree. Check them with lint, typecheck, build or the specific tests that cover the change. If a CI fix does not work out after a reasonable attempt, stop trying, leave the tree as it was before that attempt and say what you found.
6. **Commit and push once.** One commit for the round (the merge from step 2 is its own commit already), with a message that says what was addressed. `git fetch` once more first: if the default branch or the PR branch moved (the merge bot also updates branches), merge again before you push. `git push` normally. If the push is rejected, fetch, merge and retry once; never force.
7. **Answer and resolve.** For each thread you fixed or declined, reply on it (`gh api graphql` with `addPullRequestReviewThreadReply`, `pullRequestReviewThreadId` and a short body: "Fixed in <short sha>: <what>" or "Not changing this: <reason>") and then resolve it with `resolveReviewThread` (`threadId`). Leave the threads you chose to Leave untouched: no reply, not resolved.
8. **Report.** Finish with a short summary: what was merged in, which comments were fixed, which were declined and why (so the user can reopen them), which were left for a human, which CI failures were fixed or could not be, and the commit you pushed. If nothing needed doing, say so and stop.

capcom watches the PR on GitHub, so it sees the new commit and the resolved threads on its own: there is nothing to record on the board.
